## Install the published validation baseline

```sh
go install github.com/jdbencardinop/tesseraworkspaces/cmd/tws@v1.2.18-rc.9
tws --version
```

Expected:

```text
tws version v1.2.18-rc.9
```

The new scoped standalone push route requires Git 2.45+; legacy push and sync
requirements are unchanged. Use the same current binary throughout any active
or recoverable operation.

## 1. Configured-base creation

Test in a repository where the current branch differs from the intended base:

```sh
tws add rc-base-test
tws new rc-base-test local-master --base master
tws new rc-base-test remote-master --base origin/master
tws stack rc-base-test
```

Verify each worktree starts at the requested ref:

```sh
git -C <local-master-worktree> rev-parse HEAD
git rev-parse master

git -C <remote-master-worktree> rev-parse HEAD
git rev-parse origin/master
```

Also test a tag or commit SHA and an invalid ref. Invalid refs must not create a worktree or stack entry.

## 2. Feature-directory repo inference

From a feature that already has one worktree:

```sh
cd <workspace>/<feature>
tws new <feature> second --base master
```

Expected: tws infers the single source repo. For a multi-repo feature, omitting `--repo` must fail with an ambiguity message.

## 3. Conflict continuation

Create or use a parent/child stack and trigger a real conflict in a middle branch:

```sh
tws sync <feature>
# resolve conflict in the reported worktree
git add <files>
git rebase --continue
tws sync <feature> --continue
```

Expected:

- the resolved branch is acknowledged;
- all deferred descendants are processed;
- a later conflict retains `.sync-state.yaml` and can be continued again;
- `Sync complete` appears only when relevant parent-child ancestry is current;
- `--push` runs only after complete sync.

## 4. Decoupled branch identity

Configure a prefix:

```sh
tws config set branch_prefix 'juanbe/feature/' --repo
tws add rc-prefix -n pr1
```

Expected:

- worktree path ends in `worktrees/pr1`;
- Git branch is `juanbe/feature/pr1`;
- `tws doctor` and `tws sync` do not report a false branch mismatch.

## 5. Regression checks

Exercise:

```sh
tws add <feature> -n <branch>
tws new <feature> <child> --base <branch>
tws sync <feature> --push
tws archive <feature> <branch>
tws open <feature> --feature-dir --no-agent
tws open <feature> --all
```

Confirm multi-repo features, archived branches, quick-start, inject files, hooks, and decisions still behave normally.

## 6. v1.2.18 regression boundaries

Cover both external and checkout modes where supported, including refusal and
interruption cases rather than only successful commands:

| Area | Required coverage |
| --- | --- |
| Ordinary sync safety (#4) | Abort restores attributable local effects before publication; a push attempt makes recovery forward-only. Unsafe replay cutoffs refuse without guessing or discarding evidence. |
| Slash-containing injection (#1) | External injection reaches only verified linked worktrees, including slash-containing logical names; checkout injection still refuses. |
| Scoped status (#3) | Named status avoids unrelated feature inventories and probes; failed or timed-out observations remain unknown rather than healthy. |
| Templates and conflict resolution (#2 and rc.6) | Independent role selections, default-No removal consent, remembered keep/edit decisions, and refusal of unmanaged files, symlinks, permission drift, and unresolved recovery. |
| External rename (#5) | Dirty work and Git backpointers survive a future rename; interruptions use exact journal-bound recovery. Older broken layouts are not silently repaired. |
| Scoped standalone push (#6) | Exact entry/subtree selection in both modes, refs without materialized worktrees, offline dry-run, frozen leases, and continuation without republishing confirmed successes. Cancellation never rolls back remote refs. |
| Reparent completion (#7) | A selected external root and the target entry's repository supply candidates. Missing/unknown target context never borrows unrelated Git refs; completion stays read-only and local-only. |
| Checkout metadata movement | Failed rename or one/all migration retains unresolved movement/registry evidence and blocks mutations and launches, even if the shared lock is absent. Only verified completed evidence is nonblocking. |

Guided checkout metadata recovery is requested separately as
[`checkout-metadata-move-recovery`](../.tpatch/features/checkout-metadata-move-recovery/request.md).
It is not a shipped recovery command. Preserve and reconcile the exact evidence
as described in [configuration guidance](configuration.md); publication
continuation/cancellation does not recover metadata movement.

## Promotion criteria

Before publishing stable `v1.2.18`:

- at least two representative feature stacks complete multiple create/sync
  cycles, with external and checkout coverage;
- one real conflict is successfully resumed through descendants;
- no wrong-base or false branch-identity regressions are reported;
- the current RC boundaries above have focused regression coverage;
- no P0/P1 blocker remains from RC testing, and intentional limitations remain
  documented rather than being presented as completed follow-ups;
- the changelog, roadmap, workflow handoff, and release checklist agree on
  `v1.2.18` as the stable target; the baseline install command and its expected
  version remain rc.9 until the new tag is actually available.

Run the [required gates](engineering-workflow.md#required-gates) against the
final candidate and again after landing. Obtain approval for the clean landed
commit before push/tag; verify successful Ubuntu/macOS main CI before tagging,
then verify tag/release CI and the exact-tag binary version before declaring a
release published. Updating this guide does not itself authorize publication.
