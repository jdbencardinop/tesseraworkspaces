# Specification: transactional ordinary-sync abort

## Problem statement

An ordinary `tws sync` run can move an earlier selected branch and update `stack.yaml`, then stop when a later branch conflicts or validation fails. The current `--abort` paths only abort the active rebase and restore the immediate checkout; they do not restore every branch and metadata effect owned by the run. A successful-looking abort can therefore leave completed anchors or descendants advanced. The fix must make each new ordinary-sync run a durable, closure-aware recovery transaction without changing rebase cutoff selection, safe-reparent semantics, or successful no-flag behavior.

## Acceptance criteria

1. **Durable preimage before mutation.** Before the first selected-branch Git mutation in external or checkout mode, sync persists a versioned run identity, frozen selection/policy, exact pre-run `stack.yaml` bytes, original checkout/holder state, and the full object ID of every selected branch. Every saved object is pinned by a durable Git ref in its repository/common-dir before mutation so Git GC cannot remove it. Missing branches, unsafe holders, unsupported repository aliases, or inability to persist/pin any preimage refuse the run before branch mutation.
2. **Complete selected closure and repository identity.** The snapshot uses logical entry names for stack identity and `StackEntry.GitBranch()` for Git refs, includes materialized and archived entries in the frozen selection, records canonical repository/common-dir identity for each effect, and supports external stacks spanning multiple repositories plus checkout mode's single repository/physical checkout contract.
3. **Run-owned mutation journal.** The recovery record persists, with durable atomic writes, action intent before each effect, authoritative observed post-image/progress after it, metadata intent, validation intent and before/after ref/checkout images, publication intent/progress, rollback progress, and cleanup progress. Loaders distinguish absent legacy state from corrupt, unreadable, or unsupported new evidence and fail closed for the latter. State writes/removals in changed paths are never ignored or converted to success. A validator may create ordinary build/test outputs, but it may not move refs or switch/detach the checkout; detected or interrupted validator mutation preserves the journal and work and requires manual recovery rather than automatic adoption or rollback.
4. **Git effect accounting.** The implementation investigates and records every branch ref movement attributable to the run, including selected branches completed before a later failure, current rows, and collateral refs moved by `git rebase --update-refs`. Fetch-created or fetch-updated refs are not claimed as rollback-owned effects. If an effect cannot be safely attributed and protected, sync refuses before that effect rather than disabling established sync flags or claiming arbitrary concurrent ref movement.
5. **Crash reconciliation.** If the process stops between journal intent, Git mutation, metadata write, or progress update, `--continue` and `--abort` reconcile the journal from authoritative refs, worktree state, and Git rebase evidence. They do not infer success solely from an expected target SHA. An interrupted rollback is resumable and idempotent.
6. **Ownership-protected rollback.** Every rollback ref write is compare-and-swap protected against the recorded run-owned post-image. Deletion, identity change, an unexpected current value, later user commits, or an unsafe dirty holder causes an explicit refusal before any rollback mutation. Rollback never uses `git reset --hard`, force checkout, auto-stash, global Git config, broad cleanup, or remote-ref mutation.
7. **Rollback preflight and effects.** Abort preflights all required repositories and holders before restoring any effect. Subject to that preflight, it restores every run-owned branch ref (including completed anchors and collateral refs), exact `stack.yaml` bytes, and each mode's original checkout/holder state. Ref transactions are per repository; the CLI does not claim cross-repository crash atomicity. Output identifies effects completed, pending, or refused.
8. **Recovery-state lifecycle.** Once rollback starts, `--continue` refuses to resume forward rebases and directs the user back to `--abort`. Recovery journals, snapshot refs, locks, and compatibility envelopes are removed only after every owned effect and holder state is restored. Cleanup failure preserves enough evidence for safe repeated abort.
9. **Publication and completion boundaries.** Immediately before the first sync-owned push attempt, including an attempt that fails or has an unknown outcome, sync durably records a publication marker and push intent/progress. Thereafter `--abort` refuses local rollback, preserves evidence, and guides `--continue` or manual recovery; it never rewrites remote refs. All ordinary-sync push paths propagate failures without deleting the only recovery record. As explicitly approved after the GC-retention audit, a no-push run remains abortable until all forward effects succeed and a forward-complete decision is durably written, before any preimage pin is deleted. After that decision, either recovery verb only completes cleanup and reports that sync already completed; it never rewinds refs/metadata or overwrites subsequent user work. Cancellation before mutation has a distinct cleanup-only decision and must not claim that forward work completed.
10. **Legacy compatibility and downgrade safety.** Existing in-progress runs without transactional snapshots retain legacy continue/abort behavior, but legacy abort emits an explicit warning that earlier branch movements cannot be fully restored. New evidence has a format/version and compatibility envelope that older readers cannot silently resume without rollback guarantees. Unknown, malformed, corrupt, or downgraded new state fails closed. Existing safe-reparent compatibility envelopes are not treated as sync rollback state.
11. **Concurrency and exclusions.** External sync retains the shared feature mutation lock through Git, metadata, optional push/remote follow-up, and final cleanup. Checkout sync retains its global mutation reservation. Reparent and session-launch exclusions remain enforced. Fresh mutations detect orphaned/recoverable transactional sync state even if the advisory lock is missing.
12. **Modes and routes.** The contract covers default/no-flag sync, explicit `--full` and `--local-only`, `--only` and `--from`, guarded and unguarded execution, initial runs, `--continue`, and `--abort` in both workspace modes. It preserves validation behavior, logical/Git branch-name decoupling, archived entries, external multi-repository operation, and existing successful stdout/stderr except where failure/recovery messaging intentionally changes. The sole approved compatibility exception is external no-stack legacy sync when `stack.yaml` is genuinely absent: it requires an interactive warning and explicit confirmation or `--allow-nontransactional`, refuses by default in noninteractive use, is invalid with plan/guard/recovery/scoped routes, and is documented as nontransactional with no complete rollback. Existing unreadable or malformed metadata always refuses.
13. **Metadata correctness.** External and checkout abort restore byte-for-byte pre-run `stack.yaml`; forward progress only publishes metadata through journaled intent and durable write. The implementation does not conflate refs, metadata, and worktree/index state into one atomic effect.
14. **Observability and guidance.** Existing status/doctor/readback conventions surface pending, partially rolled-back, validation-mutated, published, cancelled-before-mutation, and forward-complete cleanup-only ordinary-sync runs with phase-correct continue/abort/manual-recovery guidance. Unreadable, malformed-before-version, and unknown evidence is always preserved for inspection rather than paired with destructive deletion advice. CLI help, README, changelog, and directly related embedded skills describe transactional abort, publication refusal, validator immutability, the explicit no-stack exception, legacy limitations, and per-repository atomicity honestly.
15. **Behavior tests.** Real temporary repositories, local bare remotes, and real worktrees cover the six-branch `master -> pr1 -> {pr2,pr3,pr4}; pr3 -> pr5 -> pr6` conflict-after-anchor scenario in external and checkout modes, asserting every branch ref and exact metadata bytes after abort. Additional deterministic tests cover full/local-only, no-flag, only/from, guarded/unguarded, archived and decoupled names, multi-repository stacks, collateral `--update-refs`, conflict and validation failures, successful continue, later user movement refusal, dirty-holder refusal, missing/corrupt evidence, publication-before-first-attempt, first-push failure retention, legacy warnings, unknown/downgrade failure, crash injection around meaningful journal/Git/metadata/rollback/cleanup transitions, and repeated abort recovery. Tests configure Git identity in the actual test command environment and assert rendered command output, not only internal labels.
16. **Required verification.** The candidate passes focused transactional sync tests, then sequentially: `go test ./internal ./internal/cli -count=1 -timeout=20m`; `GIT_CONFIG_COUNT=0 GIT_CONFIG_NOSYSTEM=1 go test ./... -count=1 -timeout=40m`; `GIT_CONFIG_COUNT=0 GIT_CONFIG_NOSYSTEM=1 go vet ./...`; `golangci-lint run ./...`; `make build`; `gofmt` on changed Go files; `git diff --check`; and `tpatch feature deps --validate-all`.

## Recovery admission refinements

- A valid transactional payload without its compatibility marker can recover
  through the same phase-correct verbs. Recovery reclaims the recorded owner,
  revalidates the payload, and exclusively restores the missing marker before
  further forward or rollback work. Plain inspection/refusal writes nothing.
- Mixed real legacy and transactional records remain manual-recovery-only;
  preserve both artifacts and never recommend deleting either.
- The explicitly consented no-stack executor must recheck recovery state under
  its own guard and recheck stack absence immediately before execution. It never
  dispatches back into the stack executor. Publishing requires stack metadata.
- After validator checkout mutation, doctor retains wrong-branch/dirty/ancestry
  facts but suppresses automatic checkout/rebase/commit/stash repair hints.

## Out of scope

- Changing how old-parent cutoffs are chosen, validated, or displayed; `sync-cutoff-integrity` owns that defect.
- Changing remote refs during rollback, making remote publication reversible, or rewriting standalone `tws push` behavior.
- Replacing safe-reparent's transaction model or creating a generic transaction framework.
- Claiming cross-repository crash atomicity or ownership of arbitrary concurrent ref movement.
- Changes to Lane B, tesserasessions, shared mailboxes, scoped status projection, injection, templates, or adjacent backlog features.

## Implementation plan

1. Extend ordinary-sync recovery formats and compatibility classifiers in `internal/sync_run_state.go`, `internal/checkout_sync.go`, and their readback/status paths with a versioned transactional journal, snapshot identities, publication/rollback phases, and strict loading.
2. Reuse existing atomic-write, canonical repository/common-dir, ref-transaction/CAS, worktree-holder, lock, and pinning patterns from sync and safe-reparent code; add narrowly scoped sync journal helpers where reuse is not possible.
3. Freeze and pin preimages before mutation in external and checkout dispatch, journal per-effect intent and observed results around rebase/metadata/push, and preserve recovery evidence on every failure path.
4. Replace new-run abort behavior with preflighted, ownership-protected, resumable restoration of refs, metadata, and holders; keep an explicit truthful legacy abort path for old artifacts.
5. Integrate forward-only publication handling, continue-versus-rollback exclusion, orphaned-state detection, status/doctor projection, CLI help, README/changelog, and embedded sync skills.
6. Add focused unit and real-repository integration fixtures for all acceptance paths, run formatting and the complete sequential validation matrix, and leave the feature in implementation-started state for parent audit.
